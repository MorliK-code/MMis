# План внедрения runtime-памяти и когнитивного слоя для MMis

## 1. Что именно мы делаем

Цель этого этапа — не ломать текущую идею `memory_core` как отдельного подпроекта, а усилить её так, чтобы:

- снаружи для пользователя оставался **один чат**;
- внутри память была **структурированной**, а не плоской;
- свежая continuity была доступна **сразу**, без ожидания фонового воркера;
- тяжёлая обработка памяти оставалась **асинхронной**;
- дальше на этой базе можно было строить уже **когнитивный слой Аси**.

Главная мысль:  
**очередь остаётся**,  
**вторая тяжёлая LLM не нужна**,  
**быстрый runtime-слой памяти добавляется внутри самого `memory_core`**.

---

## 2. Базовые принципы, на которых строим решение

### 2.1. Один чат снаружи, много структур внутри
Для пользователя остаётся один основной чат.  
Для памяти этот чат должен распадаться на внутренние сущности:

- stable profile
- preferences
- active task / active thread
- episode events
- emotional states
- identity core
- long-term semantic memory

### 2.2. Запись памяти и чтение памяти — разные процессы
Нельзя пытаться решать continuity только через long-term pipeline.

Правильная схема:

```text
user_message
-> sync runtime/session write
-> retrieval (runtime + active thread + profile + long-term)
-> answer
-> async background consolidation
```

### 2.3. Continuity должна быть дешёвой
Continuity не должна зависеть от второй тяжёлой модели.  
Она должна жить на:

- простом sync store
- правилах
- лёгкой нормализации
- минимальном runtime state

### 2.4. Heavy memory остаётся в фоне
Асинхронный worker по-прежнему отвечает за:

- extraction
- normalization
- dedupe
- embeddings
- governor
- consolidation
- long-term artifacts

---

## 3. Что именно надо получить в конце

После внедрения система должна уметь:

1. помнить последние 1–3 хода сразу, без ожидания фоновой записи;
2. не тащить в каждый prompt мусор и слабые факты;
3. различать типы памяти;
4. резать длинный чат на скрытые эпизоды;
5. выдавать retrieval не только из long-term, но и из runtime слоя;
6. быть готовой к persona bridge, identity core и planner-логике.

---

## 4. Этапы сборки решения

# Этап 0. Подготовка и фиксация текущего состояния

## Задача
Перед любыми изменениями надо зафиксировать, как память работает сейчас.

## Что сделать
- снять текущий flow:
  - `ingest_event`
  - очередь
  - worker
  - retrieval
  - prompt build
- определить, где именно сейчас происходит lag между новым сообщением и памятью;
- собрать минимальные сценарии регрессии:
  - продолжение одной темы подряд;
  - смена темы;
  - возврат к старой теме;
  - эмоциональный эпизод;
  - активная задача.

## Результат
Есть документ или тестовый список:  
**“как память ведёт себя до внедрения runtime-layer”**.

# Этап 1. Добавить sync runtime/session слой внутри memory_core

## Задача
Сделать быстрый слой памяти, который не требует фонового воркера и не требует отдельной большой модели.

## Что создать
Новый модуль, например:

```text
memory_core/runtime_session_store.py
```

## Что он должен хранить
Минимальный runtime state на активную сессию:

- `last_user_turn`
- `last_assistant_turn`
- `active_topic`
- `active_task`
- `open_questions`
- `recent_decisions`
- `recent_user_state`
- `current_episode_id`
- `last_turn_ts`

## Что важно
Этот слой:
- пишется **синхронно**;
- лёгкий;
- не делает embeddings;
- не зависит от worker;
- не заменяет long-term memory.

## Что менять
### В `memory_core/facade.py`
Внутри `ingest_event()`:
1. сначала синхронно обновлять `runtime_session_store`;
2. только потом ставить job в очередь.

## Критерий готовности
После нового user turn следующий ответ уже может использовать свежую continuity, даже если worker ещё не отработал.

---

# Этап 2. Ввести типы памяти

## Задача
Память должна перестать быть “свалкой фактов”.

## Минимальные типы
Ввести хотя бы 5 типов:

- `profile_fact`
- `preference`
- `episode_event`
- `task_state`
- `emotional_state`

Дополнительно сразу стоит зарезервировать:
- `identity_core`
- `system_note`
- `project_context`

## Зачем это нужно
Чтобы retrieval и retention были разными для разных сущностей.

Пример:
- `profile_fact` → хранить долго;
- `task_state` → хранить до завершения;
- `emotional_state` → хранить кратко, подмешивать только по условиям;
- `episode_event` → использовать для continuity и возврата к теме.

## Критерий готовности
Каждая новая memory artifact сущность имеет:
- `type`
- `scope`
- `priority`
- `decay`
- `retrieve_when`

# Этап 3. Добавить hidden episodes внутри одного внешнего чата

## Задача
Не делать новые UI-чаты, а делить внутреннюю память на главы.

## Как это должно работать
Пользователь видит один чат.  
Память внутри режет поток на эпизоды:

- разговор про память
- разговор про интерфейс
- разговор про железо
- разговор про настроение
- разговор про Telegram-бота
- разговор про Ollama / модели
- разговор про UI / persona

## Что создать
Например:

```text
memory_core/episode_manager.py
```

## Что он должен делать
- открывать новый эпизод при явной смене темы;
- продолжать текущий эпизод, если тема та же;
- связывать `runtime_session_store` с `current_episode_id`;
- уметь возвращать:
  - текущий эпизод
  - последний релевантный эпизод
  - короткую сводку эпизода

## Как не усложнять
На MVP не нужна LLM-классификация на каждый ход.  
Достаточно:
- простых эвристик,
- topic hints,
- similarity к активной теме,
- явных user-индикаторов вроде “вернёмся”, “кстати”, “ещё по тому же поводу”.

## Критерий готовности
Retrieval больше не ищет по одной бесконечной ленте, а умеет опираться на эпизоды.

# Этап 4. Изменить query path: retrieval должен читать runtime + long-term

## Задача
Сейчас retrieval не должен смотреть только в long-term или только в worker artifacts.

## Что менять
### В `memory_core.query()`
Нужно сделать merge нескольких источников:

1. `runtime_session_store`
2. active episode
3. stable profile
4. active/open task state
5. long-term retrieval
6. optional pending artifacts

## Правильный порядок
Сначала самые свежие и дешёвые слои, потом дальняя память:

```text
runtime_session_store
-> active episode
-> active task
-> profile / preferences
-> long-term retrieval
-> rerank / merge / trim
```

## Отдельно
Подключить уже существующий, но неиспользуемый флаг:

```text
include_pending_facts_in_retrieval
```

Если включён:
- query path должен домешивать pending/runtime слой в retrieval pack.

## Критерий готовности
На следующем ходе система видит:
- текущую тему,
- текущую незавершённую задачу,
- последние решения,
- свежий эмоциональный контекст,
даже если фоновой индексации ещё нет.

---

# Этап 5. Оставить worker для heavy memory и не пытаться лечить continuity через него

## Задача
Не перегружать worker обязанностями, которые должны решаться сразу.

## Worker должен делать только это
- extraction
- normalization
- entity resolution
- dedupe
- conflict prep
- embedding
- long-term upsert
- episode consolidation
- profile consolidation

## Worker не должен быть единственным источником continuity
Continuity уже должна жить до него.

## Что важно
Не пытаться “починить” всё уменьшением poll interval.  
Это не решит корневую проблему.

## Критерий готовности
Если worker задержался или временно не успел — continuity в диалоге всё равно не разваливается.

---

# Этап 6. Сделать retrieval-правила по типам памяти

## Задача
Не всё должно тащиться в prompt одинаково.

## Правила для MVP
### `profile_fact`
- всегда может участвовать;
- высокий приоритет;
- без быстрого decay.

### `preference`
- подмешивать, если влияет на стиль ответа или формат;
- обновлять аккуратно, не перезаписывать резко.

### `task_state`
- высокий приоритет, пока задача активна;
- после завершения переводить в episode summary.

### `episode_event`
- нужен для локальной continuity и возврата к теме;
- приоритет средний.

### `emotional_state`
- не тащить всегда;
- retrieve only if:
  - текущая тема связана с эмоцией,
  - это follow-up той же сцены,
  - нужен поддерживающий ответ.

### `identity_core`
- почти всегда учитывать;
- менять только через подтверждение или очень сильный сигнал.

## Критерий готовности
Фразы типа “мне плохо” больше не превращаются в вечный глобальный факт о пользователе.

# Этап 7. Исправить сломанный учёт результата ingest

## Задача
Сейчас статистика памяти не должна врать.

## Что поменять
Если `_capture_memory_ingest()` читает данные как объект, а `ingest_event()` возвращает `dict`, нужно сделать совместимость.

### Исправить так
Либо:
- вернуть нормальную dataclass/typed object из `ingest_event()`

Либо:
- научить `_capture_memory_ingest()` понимать и `dict`, и object.

## Зачем это важно
Иначе будет ложная картина по:
- stored ids
- promoted ids
- dropped ids
- качеству записи памяти
- debug telemetry

## Критерий готовности
Метрики записи памяти отображают реальное состояние pipeline.

# Этап 8. Добавить Memory Inspector / Debug UI

## Задача
Сделать отладку памяти прозрачной.

## Что показать в интерфейсе
Минимально:

- какие memory items были retrieved;
- откуда они пришли:
  - runtime
  - episode
  - profile
  - long-term;
- какие были отброшены;
- какой у них тип;
- почему они были выбраны;
- superseded ли они;
- какой episode сейчас активен.

## Зачем
Без этого ты постоянно будешь смотреть на ответ и гадать:
“почему она это вспомнила / не вспомнила?”

## Критерий готовности
У каждой странной реплики можно быстро понять источник memory pack.

# Этап 9. Поверх этой базы начать строить когнитивный слой

Этот этап не обязателен для первой итерации, но его надо заложить в архитектуру сразу.

## 9.1. Memory Governor
Нужен модуль наподобие:

```text
memory/governor.py
```

Функции:
- искать конфликты фактов;
- помечать старые версии как `superseded`;
- учитывать temporal grounding;
- пересобирать профиль.

## 9.2. Profile Stabilizer
Нужен слой наподобие:

```text
profile_evolution.py
```

Функции:
- разделять persistent traits и volatile preferences;
- делать confidence decay;
- стабилизировать личность и предпочтения.

## 9.3. Memory → Persona bridge
Нужен слой наподобие:

```text
persona_context_builder.py
```

Функции:
- строить persona snapshot;
- смешивать character + user profile + active context;
- передавать это в prompt builder.

## 9.4. Episodic Planning Memory
Нужен слой наподобие:

```text
episode_planner.py
```

Функции:
- помнить незакрытые задачи;
- возвращаться к ним;
- поддерживать длинные проектные ветки;
- формировать следующее действие.

## 9.5. Identity Core
Добавить отдельный тип памяти:

```text
identity_core
```

Туда складывать:
- стиль общения;
- как называть пользователя;
- формат ответов;
- устойчивые границы;
- важные личные настройки.

## 7. Что нельзя делать

Чтобы не сломать архитектуру, не надо:

- переносить runtime continuity обратно в основной проект вне `memory_core`;
- добавлять вторую тяжёлую LLM только ради свежей памяти;
- пытаться пихать всю память в prompt всегда;
- использовать worker как единственный источник актуальной continuity;
- превращать любой эмоциональный эпизод в постоянный user fact;
- дробить UI на реальные новые чаты ради решения проблемы памяти.

## 8. Критерии успеха

Решение считается рабочим, если выполняются все условия ниже.

### 8.1. Continuity
- модель на следующем ходе помнит свежую тему без задержки;
- может продолжить текущую задачу без “мы как будто начали заново”.

### 8.2. Garbage control
- слабые и одноразовые факты не забивают prompt;
- старые эмоции не всплывают без причины.

### 8.3. Структура
- память делится по типам;
- длинный чат режется на эпизоды;
- retrieval учитывает scope и retrieve rules.

### 8.4. Debuggability
- можно увидеть, почему конкретный факт попал в ответ;
- можно отследить путь от события до retrieved context.

### 8.5. Расширяемость
- на базе этой памяти можно без ломки добавить:
  - governor,
  - profile stabilizer,
  - persona bridge,
  - planner,
  - identity core.

---

## 9. Итог

Правильный путь для MMis сейчас такой:

- не отказываться от отдельного `memory_core`;
- не выкидывать очередь и worker;
- не добавлять вторую тяжёлую модель;
- добавить **быстрый sync runtime слой памяти внутри memory_core**;
- сделать **hidden episodes**;
- разделить память по типам;
- научить retrieval собирать memory pack из нескольких слоёв;
- после этого строить уже **когнитивный слой Аси**, а не пытаться всё чинить одним prompt.

Это и будет нормальная база для:
- сильной continuity,
- правдоподобной долгой памяти,
- стабильного характера,
- дальнейшего перехода от “умного чата” к “личному ассистенту”.
