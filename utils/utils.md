# utils.md

## Зачем нужен `utils/`
`utils/` — это общий инфраструктурный слой проекта.  
Он нужен, чтобы не дублировать служебную логику (логирование, кеш, метрики, валидация, таймеры) по разным модулям (`llm`, `memory`, `modules/*`, `ui`).

Практически это дает:
1. Единые правила и формат для всех подсистем.
2. Меньше копипасты и проще поддержка.
3. Более предсказуемое поведение (одинаковый логгер, одинаковые проверки и ограничения).

## Зачем каждый файл

### `utils/logger.py`
Назначение: централизованное логирование.

Что делает:
1. `get_logger(name)` выдает логгер с нормализованным именем канала.
2. `configure_logging(...)` настраивает вывод в консоль и в файл.
3. `log_json(logger, event, **payload)` пишет структурированные JSON-события.

Зачем это в проекте:
1. LLM-провайдеры логируют payload и служебные события в одном формате.
2. Модули памяти, UI, voice, tools пишут логи одинаково.
3. Проще дебажить и фильтровать события.

### `utils/cache.py`
Назначение: TTL-кеш на диске + горячий кеш в памяти.

Что делает:
1. `DiskTTLCache.get/set/delete` для быстрых повторных чтений.
2. Хранит записи по namespace и ключу.
3. Автоматически отбрасывает просроченные данные.

Зачем это в проекте:
1. Снижение числа повторных сетевых вызовов (поиск/скрейпинг/метаданные).
2. Быстрее ответы на повторяющиеся запросы.
3. Меньше нагрузка на внешние сервисы.

### `utils/metrics.py`
Назначение: легковесные метрики процесса (in-memory).

Что делает:
1. Counters: `inc(...)`.
2. Gauges: `set_gauge(...)`.
3. Histograms: `observe(...)` + сводка (`p50`, `p95`, `avg`, и т.д.).
4. `snapshot()` и `dump_jsonl(...)` для экспорта состояния.

Зачем это в проекте:
1. Замер производительности и здоровья пайплайна.
2. Контроль задержек и частоты событий.
3. Диагностика деградаций без сложной внешней телеметрии.

### `utils/timers.py`
Назначение: замер времени выполнения блоков и функций.

Что делает:
1. `Timer` (context manager) с авто-записью в метрики.
2. `measure_time()` для обратной совместимости старого кода.
3. `timed_block(...)` и декоратор `timeit(...)`.
4. `now_ms()` для timestamp в миллисекундах.

Зачем это в проекте:
1. Быстро померить latency конкретного участка.
2. Стандартизовать тайминг-инструменты в кодовой базе.
3. Упростить профилирование узких мест.

### `utils/validators.py`
Назначение: базовые проверки и ограничения входных данных.

Что делает:
1. Валидация схем tool-call (`validate_tool_call_schema`).
2. Валидация обновлений профиля (`validate_profile_update`).
3. Безопасная проверка пути внутри разрешенной директории (`safe_path`).
4. Кламп параметров генерации (`clamp_params`) по безопасным диапазонам.

Зачем это в проекте:
1. Предотвращение кривых входных данных и падений.
2. Защита от path traversal в файловых операциях.
3. Стабильные границы параметров LLM.

### `utils/__init__.py`
Назначение: единая точка экспорта утилит.

Что делает:
1. Реэкспортирует ключевые классы и функции (`__all__`).
2. Позволяет импортировать утилиты из одного места.

Зачем это в проекте:
1. Упрощает импорты в остальном коде.
2. Фиксирует публичный API пакета `utils`.

## Где это реально используется
1. `llm/*_provider.py`: логирование запросов и ответов.
2. `modules/internet/*`, `metadata/metadata_extractor.py`: дисковый TTL-кеш.
3. `memory/*`, `ui/api_client.py`, `modules/voice/*`: стандартный логгер.
4. `tests/test_utils_infra.py`: контракт и корректность работы всего `utils`.

## Кратко
`utils/` — это инфраструктурный фундамент проекта: наблюдаемость, надежность и повторное использование общего кода.
